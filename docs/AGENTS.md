# Documentation scope

Follow the root `AGENTS.md`. Documentation must be decision-useful, traceable, and honest about evidence.

- Put claims in the correct evidence class: marketing/documented behaviour, observation, user report, inference, or decision.
- Date time-sensitive research and cite direct sources near the claim. Prefer official/primary sources for technical behaviour.
- Use stable requirement, rule, test, decision, and ADR identifiers where implementation depends on wording.
- State uncertainty, validation gaps, conflicts, and the cost of being wrong.
- Keep product scope, domain rules, architecture, design, and quality guidance in their own directories; link instead of duplicating normative text.
- A document is not `accepted` until the product owner or designated decision owner records that status.
- Do not turn illustrative prototype data into product evidence or analytics claims.
- Run link, placeholder, required-section, and terminology checks after broad edits.
